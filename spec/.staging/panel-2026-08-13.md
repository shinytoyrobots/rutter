## Divergence 1 — What does "the same sentinel channel session directives use" (SCN-010) / "the capture sentinel channel" (SR-047) actually require? (SCN-010, SR-047)

**The fork, restated with a materially new finding:** this is the same underlying question `dissent-2026-08-13-0003` fought over at the population level (shared tag vs. distinct tag) — but this panel demonstrates it is **still live in the current spec text**, unchanged since v3.12.0 despite two full implementation variants, a chavruta round, and two spec amendments (v4.0.0, v5.0.0) having passed through this exact scenario since. The text SCN-010 actually ships today still literally says positions ride "the same sentinel channel session directives use," while the shipped code uses a *distinct* `<!-- librarian-position ... -->` tag. Spec and implementation currently disagree on their own record.

Five independent readers, none shown the shipped code or the dissent history, split three ways:

- **Reading A — shared literal tag** (0 of 5): no reader committed to this, though multiple flagged it as textually defensible and not ruled out.
- **Reading B — same general mechanism, distinct tag per kind** (4 of 5 — R1, R2, R4, R5): HTML-comment-wrapped, Stop-hook-scanned, but positions get their own tag name (e.g. `librarian-position`), parallel to `librarian-session`. **This matches what actually shipped.**
- **Reading C — bare, unwrapped line, no HTML comment at all** (1 of 5 — R3): the grammar block is rendered with zero comment-delimiter syntax anywhere, in contrast to the background section's explicit `<!-- librarian-session {...} -->` example — R3 read that contrast as deliberate and committed to positions riding as a plain, un-wrapped line in the visible turn output. **This matches neither the plan nor the shipped code — a third live reading nobody had named before.**

**Why this matters:** 4-of-5 converging on the shipped answer is a meaningfully positive signal that Reading B is the more natural reading of the current prose — but 1-of-5 landing on a genuinely different, previously-unarticulated reading (C) means the text is not yet tight enough to foreclose it, and the text's own literal words ("the same... channel") still don't say what shipped. This is exactly the kind of fork a panel exists to locate cheaply — R3's reading cost one Explore-agent call to surface; the same fork cost a full gen-3 population + chavruta round to surface the first time.

**Proposed disambiguation:** amend SCN-010's When-clause and SR-047 to state plainly that the position directive rides its own distinct sentinel tag (name it, or reference wherever the tag name is now canonically defined — e.g. `src/positions.ts`'s constant), sharing only the general mechanism (HTML-comment marker, Stop-hook-scanned) with session directives, explicitly ruling out both Reading A (shared tag) and Reading C (unwrapped line). Route: `/flow-spec amend SCN-010, SR-047`.

**Relationship to existing dissent:** `dissent-2026-08-13-0003`'s reactivation condition 1 (`SCN-010 acceptance-criteria text or SR-047/SR-048/SR-052 changes vs v4.0.0`) would fire on this amendment — expected and correct, since this is precisely the wire-format question that dissent is watching. The amendment should explicitly resolve toward the dissent's own `provisional-resolution` (distinct tag, marked provisional pending this exact `/flow-spec` ratification) rather than reopening the shared-vs-distinct debate from scratch.

## Divergence 2 — Is SR-049's idempotence check scoped to the current month's file, or every positions file ever written? (SR-049)

**The fork:** neither the scenario prose ("leaves the positions file byte-identical," singular, no month qualifier) nor SR-049 ("a position event already recorded for that session," no scope qualifier) states whether the duplicate-check reads one file or all of them.

- **Reading A — current month only** (2 of 5 — R1, R5): cheaper, and a session's Stop-hook re-fires will almost always land within one calendar month; treating the guarantee as scoped to the file a new write would land in anyway.
- **Reading B — all months / full logical stream** (2 of 5 — R2, R4): the strict byte-identical guarantee and "regardless of how many Stop events fire" language read as an unscoped correctness promise; a scope limiter would silently permit duplicates across a month boundary, which reading B treats as unacceptable given the spec's repeated insistence on exactness elsewhere.
- **R3 did not commit either way** on this specific sub-question.

**This is not a new fork — it is `SG-2`, already known and disclosed at ship** (HANDOFF: "no test ever actually crosses a month boundary for the idempotence check, even though the shipped code deliberately scans every month"). What's new here: **the shipped code's actual behavior (scan every month, per `readAllPositionStreams()`) matches Reading B — the reading only 2 of 5 blind readers independently landed on.** That the other 3 either picked the cheaper reading or didn't commit is a real signal that the text under-specifies this in the direction that would cost a real bug if an implementer picked the majority instinct (Reading A, the cheap one) instead of what's actually needed.

**Proposed disambiguation:** amend SR-049 to state explicitly that the duplicate-check scans the full logical positions stream (all `<YYYY-MM>.md` files), not just the file a new event would be written to. This closes `SG-2` at the spec level (the code already does this; the spec should say so) and gives the eventually-written cross-month test something explicit to assert against. Route: `/flow-spec amend SR-049`.

## Divergence 3 — Where does `revises: <event-id>` live, syntactically, in the wire grammar? (SR-052, and by extension SR-048/SR-049)

**The fork:** the shown grammar — `POSITION <kind> <topic-key>: <stance>` — has no slot for `revises`. SR-052 discusses it as if it's an established, recognized piece of syntax, but never shows where it sits relative to the primary grammar. Readers who addressed this proposed genuinely different placements:

- A trailing token *inside* the same line, positioned before the final topic-key/stance-delimiting colon (R1: `<topic-key> revises:<id>: <stance>`-shaped).
- A distinct grammar element parsed separately from the stance, structurally required to avoid conflicting with byte-verbatim stance storage (R2, stated as a constraint without giving exact placement).
- A second, separate line within the same sentinel payload (R4, R5) — explicitly reasoned as the only placement that avoids stripping content back out of a byte-verbatim-stored stance.
- One reader (R2) separately noted the grammar shown has literally "no visible slot," flagging it as something to escalate to the spec author rather than resolve.

**Why this matters:** every reader who engaged with this treated it as a real gap, not a stylistic nit — and their proposed resolutions are mutually incompatible wire formats. An implementer following only this spec text could build any of three incompatible parsers, none demonstrably more "correct" by the text alone.

**Proposed disambiguation:** add an explicit acceptance criterion to SCN-010 (or a grammar amendment to SR-052) showing the literal, complete grammar including the optional `revises` slot — e.g. `POSITION <kind> <topic-key> [revises: <event-id>]: <stance>` or wherever it actually lives in the shipped implementation (`src/positions.ts`'s `deriveRevises` — check the real regex before writing the amendment, don't re-derive it from this panel alone). Route: `/flow-spec amend SR-052` (and SCN-010's grammar line if the canonical grammar block itself needs updating).

## Convergent-but-underspecified gaps (not routed as decisions; recommended for future patches)

1. **Malformed/unrecognized directive kind — reconfirmed, still open.** All 5 readers independently found the same gap the 2026-08-12 panel's gap-3 flagged (SR-047's "least-specified corner"): no SR states what happens when a `POSITION` line's kind token isn't one of the four valid words. This is `SG-9`, already disclosed at ship as non-blocking. Five-for-five reconfirmation across a fresh, blind read is a stronger signal than the original panel's 3-for-3 that this deserves an actual SR next time SCN-010 is touched, not just a watched gap.

2. **Empty topic-key — a new gap, not in the 2026-08-12 panel record.** SR-057 covers an empty/whitespace *stance*. Two readers (R3, R4) independently noticed the text never addresses an empty or whitespace-only *topic key* (e.g. `POSITION assert :some stance`) — no SR gives it the same "no directive at all" treatment SR-057 gives an empty stance. Worth a symmetric SR next time this scenario is amended.

3. **Ref-extraction syntax inside `<stance>` — carried forward unchanged from 2026-08-12's gap 2.** All 5 readers assumed `[[wikilink]]`-style markers by inference from adjacent mdbase/vault conventions, explicitly flagging that this slice's text never shows the actual marker syntax. Identical finding to the prior panel; still not amended.

4. **Topic key containing a colon — reconfirmed, matches known `SG-12`.** One reader (R1) independently rediscovered the already-known suite gap: the grammar's first-colon-wins parse mis-splits a topic key that itself contains a colon. Not raised by the other 4, but not contradicted either — R1's finding stands and matches disclosed ship debt.

## What convergence tells us

Architecture-level convergence remains strong: all 5 readers independently designed near-identical write-path shapes (a grammar-match router ahead of the existing session path, a parallel write module reusing session's provenance/ref-hashing helpers unchanged, append-only writers with no mutation code path at all). 4 of 5 also independently converged on the *actual shipped* wire-format choice (distinct HTML-comment tag) without being shown it — a meaningfully positive signal for that choice's textual defensibility, even though the spec prose itself hasn't yet been amended to state it explicitly. The two idempotence-scope readers who landed on the *actual shipped* behavior (all-months scanning) versus the two who landed on the cheaper, unshipped behavior (current-month-only) is the clearer warning sign: this is a real fork with a real, silent-failure-shaped wrong answer, not just a stylistic ambiguity.
