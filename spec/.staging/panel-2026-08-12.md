## Divergence 1 — Does `revises:` participate in SR-049's idempotence key? (SR-049, SR-052)

**The fork:** SR-049 enumerates identity as "kind, topic key, stance, and referenced note paths." It does not mention `revises:`.

- **Reading A — excluded (1 of 3 readers, R3):** `revises:` is not part of the identity key because SR-049's list is exhaustive. A second directive identical except for an added/changed `revises:` value collides with the first and is silently dropped — the new `revises:` value never lands. This reader explicitly flagged the silent-drop as "a real risk worth a follow-up SR" even while implementing it as written.
- **Reading B — included (2 of 3 readers, R1 and R2):** `revises:` is client-authored directive content the same way `stance` is, so SR-049's "directive content identical" test should cover it even though the parenthetical list doesn't name it. A directive differing only in `revises:` is a distinct directive and appends normally.

**Why this matters:** this is the one place a silent-loss bug is plausible under Reading A — a client correcting or adding a supersession link on a retry would have that correction invisibly eaten. That's in tension with this project's own stated stance (HANDOFF §1): "weighs openly, attributably, reversibly — never silently."

**Proposed disambiguation:** amend SR-049 to explicitly include `revises` (when present) in the identity tuple — i.e., state the parenthetical is exhaustive AND correct by adding the field, rather than leaving it to implication. Route: `/flow-spec amend SR-049`.

**Routed 2026-08-12 (HITL, AskUserQuestion): AMEND.** Not performed by this panel (the panel locates, never resolves) — queued for `/flow-spec amend SR-049`.

**Implemented 2026-08-12: spec v4.0.0.** See `spec/history/spec-v4.0.0-2026-08-12.md`.

## Divergence 2 — Is an empty-but-present stance a valid directive? (SR-047, and by extension SR-048)

**The fork:** what happens to `POSITION assert my-topic:` — grammar-valid up through the colon, nothing after it.

- **Reading A — valid, stored as empty string (1 of 3 readers, R1):** nothing in the acceptance criteria states a minimum stance length; "byte-verbatim" includes the empty string; inventing a minimum would itself be the kind of content heuristic SR-047 forbids.
- **Reading B — invalid, same treatment as a missing topic-key (2 of 3 readers, R2 and R3):** the fixed grammar requires both segments to be present and non-trivial; an empty stance fails to match the pattern the same way a missing topic-key would, and is treated as no directive at all (same precedent as SCN-001's unfilled-`<template>` rule) — with a stderr diagnostic per R3, silently per R2.

**Note:** all three readers *also* independently agreed a missing topic-key (no colon at all) is a grammar failure → no directive. The fork is narrower than it first looks: it's specifically about a stance that is present-but-empty after a well-formed `topic-key:`.

**Proposed disambiguation:** add an explicit acceptance criterion to SCN-010 stating whether an empty stance is (a) a valid, verbatim-empty position event, or (b) treated as no directive. Route: `/flow-spec amend SCN-010`.

**Routed 2026-08-12 (HITL, AskUserQuestion): AMEND.** Not performed by this panel (the panel locates, never resolves) — queued for `/flow-spec amend SCN-010`.

**Implemented 2026-08-12: spec v4.0.0** (as new SR-057, rather than editing SR-047 — cleaner separation from the routing rule). See `spec/history/spec-v4.0.0-2026-08-12.md`.

## Dissolved pseudo-divergence — SR-054's 40-vs-60 trigger

One reader (R2) surfaced, then talked itself into, a fork over whether "exceeds... word budget" means over-40 (target) or over-60 (ceiling), and landed on over-40 after reconsideration. The other two readers didn't flag this as live at all. Checked against the precedent SR-054 explicitly cites ("SR-034 shape"): **SR-034's own text says "exceeds... the stated word ceiling"** — the ceiling (60), not the target (40) — so this isn't actually an open question; R1 and R3's silence on it was correct by default, and R2's reconsideration introduced an inconsistency with the very requirement it was modeled on. **No amendment needed** — recommended patch-level tightening only: SCN-010's acceptance criterion could say "ceiling" explicitly instead of "budget" to remove the appearance of a fork for the next reader.

## Convergent-but-underspecified gaps (not routed as decisions; recommended for a future patch)

1. **Cross-month idempotence scope.** All three readers independently assumed the SR-049 dedupe check scans only the current month's positions file, not prior months — for a session straddling a month boundary, the spec doesn't say. Convergent by luck, not by text.
2. **Ref-extraction syntax.** SR-048 says refs are "captured by versioned identity... exactly as session refs are," but the `POSITION` grammar shown has no explicit slot for a ref — only R1 noticed and flagged this; R2 and R3 silently assumed reuse of an existing extraction mechanism without addressing where refs come from in a one-line stance. Worth a one-line clarification even though all three implementers would likely converge on the same answer if asked.
3. **Malformed-kind handling (SR-047).** All three converge on the practical answer (report + drop, never misroute to session-summary handling), but all three independently called this the spec's least-specified corner. Worth stating explicitly rather than relying on three-for-three luck holding at implementation time.

## What convergence tells us

Architecturally, all three readers designed near-identical implementations independently: a grammar-only router prepended to `capture-cli`, a new sibling write module reusing (never forking) the existing provenance and ref-hashing helpers, single-writer-serialized append order with no new tiebreak field, and a byte-diff regression test for SR-055 paired with a structural import-boundary check. That's a strong signal the spec text is tight on architecture even where two real behavioral forks exist underneath it.
